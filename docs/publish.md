# Публикация: что делает владелец

Проект живёт в публичном репозитории `github.com/morgenvor/k8s-observability-lab`,
ветка `main`. Правки кода, документов и конфигов готовит агент, но **публикация —
действие владельца**: push, поля репозитория, защита ветки и тег остаются за человеком.
Ниже — чек-лист с готовыми командами; пометка `[владелец]` означает шаг, который агент
не выполняет.

## 2. Публичность репозитория `[владелец]`

`api.github.com/repos/morgenvor/k8s-observability-lab` **без авторизации отвечает 404** —
репозиторий пока приватный. Пока это так, абсолютные `runbook_url` из писем у постороннего
не открываются, и критерий «понятно и проверяемо посторонним» не выполнен, хотя файлы
в `main` уже лежат.

```bash
gh repo edit morgenvor/k8s-observability-lab --visibility public --accept-visibility-change-consequences
```

После смены видимости история коммитов и все трекаемые файлы становятся публичными:
перед этим шагом прогони `./scripts/check.sh --strict` (скан секретов и адресов) и убедись,
что `AGENTS.md`, `CHANGELOG.md` и `.dsh/` в git не попали (`.git/info/exclude`).

**Личный адрес в метаданных истории — решение принято 2026-11-10.** Скан ворот читает
содержимое файлов и метаданные коммитов **не видит**: 96 коммитов истории подписаны личным
адресом автора, и после смены видимости он станет публичным. Владелец выбрал **принять этот
факт** (запись в `CHANGELOG.md`), а не переписывать историю: `git filter-repo --mailmap`
изменил бы все SHA, включая уже запушенный `8acbdb3`, и потребовал force-push. Для будущих
коммитов `user.email` в этом репозитории переключён на `…@users.noreply.github.com`.
Что включить в настройках GitHub перед публикацией: **Settings → Emails → Keep my email
addresses private** и **Block command line pushes that expose my email** — второе не даст
случайно закоммитить личный адрес снова.

Если решение пересмотрят до смены видимости, порядок такой: `git filter-repo
--mailmap <файл>`, затем `git push --force-with-lease origin main --tags`, и только потом
шаг 2. После переписывания истории все ссылки на коммиты в `CHANGELOG.md` станут
недействительными — их надо будет переписать (или указать, что SHA изменились).

## 4. Защита `main` `[владелец]`

Минимально полезный набор: обязательный зелёный `ci` перед слиянием. Имя проверки —
это имя джоба из `.github/workflows/ci.yml`; джоб один — `offline checks`, и он же
собирает образы (внутри `--smoke`), поэтому сборки Dockerfile отдельной проверкой
не дублируются. Если в защите остался контекст `docker build` от прежней версии
workflow, GitHub будет ждать проверку, которая больше не приходит, и PR повиснет
в «Expected» — контекст нужно заменить, а не оставить рядом.

```bash
cat > /tmp/protection.json <<'JSON'
{
  "required_status_checks": {
    "strict": true,
    "contexts": ["offline checks"]
  },
  "enforce_admins": false,
  "required_pull_request_reviews": null,
  "restrictions": null
}
JSON
gh api -X PUT repos/morgenvor/k8s-observability-lab/branches/main/protection \
  --input /tmp/protection.json
```

Компромисс: `strict: true` требует, чтобы ветка была актуальна относительно `main` —
для одиночного репозитория это лишний шаг, зато исключает «зелёный на старом коде».
`enforce_admins: false` оставляет владельцу возможность пушить напрямую; если включить
`true`, каждый коммит пойдёт через PR, а «прямой push» перестанет работать.

## 5. Прогон CI `[владелец]`

Workflow `.github/workflows/ci.yml` запускается на push в `main` и на pull request.
Локальный аналог — `./scripts/check.sh --strict`. Разница в окружении: в образе раннера
`shellcheck` и `docker` есть сразу, `yamllint` и `pyyaml` ставит отдельный шаг
(`python3 -m pip install yamllint==1.38.0 pyyaml==6.0.2` — версии пинованы, источник
истины — `.github/workflows/ci.yml`; pyyaml нужен выгрузке `PrometheusRule`),
а инструменты из `bootstrap-tools.sh` скачиваются в CI так же, как локально.

```bash
gh run list --workflow=ci.yml --limit 5
gh run view <run-id> --log-failed     # если красный
```

Ссылку на зелёный прогон нужно вписать в `CHANGELOG.md` (строка «прогон CI подтверждён») —
это требование приёмки версии.

## 6. Тег `v1.1` `[владелец]`

Тег ставится после того, как на HEAD зелёные офлайн-ворота и CI, а живые проверки версии
(доставка `page` в почту, ticket — в приёмник, heartbeat, правило Loki ruler) записаны в
`CHANGELOG.md`.

```bash
git status -sb                  # рабочее дерево чистое, main = origin/main
git tag -a v1.1 -m "v1.1: публичный runbook и README, маршрут алерта по severity с e-mail и catch-all, heartbeat пути уведомлений, Loki ruler, логовый путь без перечитывания старых строк"
git push origin main --tags
```

Аннотированный тег (не lightweight) — чтобы у версии был автор, дата и сообщение: по нему
потом видно, что именно считалось релизом.

## 7. Проверка после публикации

Порядок: сначала видимость (шаг 2), потом эти проверки. До публикации `api.github.com` и
`github.com` отдают 404 без авторизации, поэтому анкоры живьём до этого шага не проверяются —
офлайн-ворота доказывают только, что каждый фрагмент `runbook_url` совпадает с заголовком
`##`/`###` в `docs/runbook.md`.

```bash
# страница runbook отдаётся без авторизации (было 404, пока репозиторий приватный)
curl -sI "https://github.com/morgenvor/k8s-observability-lab/blob/main/docs/runbook.md" | head -1

# трекаемый набор не содержит лабораторных идентификаторов
./scripts/check.sh --strict

# README и runbook в индексе, а не только на диске
git ls-files | grep -E '^(README\.md|docs/runbook\.md)$'

# картинки доехали (README ссылается на них, ворота содержимое не читают)
git ls-files docs/images | sort

# в истории нет личных адресов автора, кроме noreply (решение 2026-11-10 — см. §2)
git log --format='%ae' | sort -u | grep -v 'users.noreply.github.com' || echo "только noreply"
```

Про якоря: `curl` фрагмент после `#` на сервер не отправляет вовсе, поэтому проверка «код 200
на ссылку с якорем» ничего не доказывает — GitHub ответит так же и на несуществующий якорь.
Соответствие «фрагмент ↔ заголовок `##`/`###`» доказывают офлайн-ворота (шаг «ссылки в
алертах»), а единственная живая проверка — один клик по ссылке «Ранбук» в письме после
публикации: он должен открыть страницу на нужном разделе.

## Что агент не делает

- не выполняет `git push`, не ставит теги, не меняет поля репозитория и защиту ветки;
- не снимает скриншоты и не добавляет файлы изображений;
- не публикует runbook в другом месте (wiki/Pages) — единственный адрес = файл в `main`.
